# 性能优化与架构拆分记录

> 日期：2026-07-09  
> 当前阶段：第一阶段已完成，后续按低风险小步拆分继续推进。

## 背景

当前项目长期采用单体 `index.php`：数据库连接、建表迁移、兼容字段补丁、API 路由、HTML 页面都集中在一个文件里。早期开发效率高，但随着模块增加，出现以下问题：

- 每个 API 请求都会经过同一个入口，容易把初始化成本叠加到所有页面加载上。
- `index.php` 文件过大，改动冲突和误伤风险上升。
- API、HTML、迁移逻辑混在一起，排查问题时边界不清。
- 后续继续增加活动、订单、画具、财务等模块时，维护成本会越来越高。

## 已完成优化

### 1. 页面/API 加载性能第一轮优化

提交：`610ff95 perf: reduce repeated page data loading cost`

内容：

- 给数据库初始化/迁移逻辑加缓存，避免普通 API 请求每次重复执行大量 `CREATE TABLE`、`SHOW COLUMNS`、`ALTER TABLE`。
- 增加常用查询索引，覆盖订单、学员、资源、员工、预约、考勤、画具销售等高频字段。
- 在前端 `api()` 封装中，对字典型 GET 接口增加短期缓存，减少切页和打开弹窗时重复请求。

验证：

- `php -l index.php` 通过。
- `node --check static/js/main.js` 通过。
- 本地 `get_stats` 接口正常返回。

### 2. 抽离数据库初始化/迁移逻辑

提交：`bfb3d19 refactor: extract schema bootstrap`

内容：

- 新增 `migrations/bootstrap_schema.php`。
- 将原 `index.php` 顶部的大段建表/迁移/索引逻辑移动到 `ensureSchema(PDO $db)`。
- `index.php` 只保留入口职责：数据库连接、加载迁移文件、调用 `ensureSchema($db)`、继续路由/API/HTML。
- 保留原有缓存机制：普通请求走轻量路径，强制迁移可以通过 `?migrate=1` 触发。

验证：

- `php -l index.php` 通过。
- `php -l migrations/bootstrap_schema.php` 通过。
- 普通接口请求：`http://127.0.0.1:5001/?action=get_stats` 正常返回，约 `135ms`。
- 强制迁移请求：`http://127.0.0.1:5001/?action=get_stats&migrate=1` 正常返回，约 `2.8s`。

## 风险与回退

### 已控制的风险

- 第一阶段没有拆业务 API，没有拆 HTML 页面，也没有改变主要请求参数。
- 数据库迁移逻辑只是从 `index.php` 移动到 `migrations/bootstrap_schema.php`。
- `ensureSchema($db)` 仍在入口执行，保证历史兼容逻辑还会被调用。
- 保留 `?migrate=1` 强制迁移入口，便于开发时主动刷新 schema。

### 仍需注意

- `migrations/bootstrap_schema.php` 仍是从原逻辑迁移出来的大块代码，内部还需要继续整理。
- 当前 schema 版本使用文件缓存控制，后续更规范的方式应该是数据库 `schema_migrations` 表。
- 继续拆 API 前，必须保证每一步都有可运行验证和 Git 提交。

### 回退方式

如果第一阶段出现问题，可以回退提交：

```powershell
git revert bfb3d19
```

如果只想临时强制重跑迁移：

```text
访问任意接口时追加 &migrate=1
```

## 后续待优化计划

### 阶段 2：规范数据库和公共函数

目标：继续瘦身 `index.php`，但仍不改业务行为。

建议拆分：

- `config/database.php`：PDO 连接配置。
- `includes/helpers.php`：`h()`、`now()`、`json()`、字符串工具等。
- `includes/order_helpers.php`：订单号生成、订单金额计算等高复用逻辑。

风险：中低。  
收益：入口更清晰，后续 API 拆分更安全。

### 阶段 3：迁移系统正规化

目标：把现在的文件缓存升级为数据库迁移版本表。

建议：

- 新增 `schema_migrations` 表。
- 每个迁移拥有独立版本号，例如 `20260709_001_create_core_tables`。
- 已执行迁移写入表中，不再依赖 `temp/schema_init.cache`。
- 保留 `?migrate=1` 作为开发入口，后续可改成 CLI 脚本。

风险：中。  
收益：可追踪、可回放、可排查数据库变更。

### 阶段 4：按模块拆 API

优先顺序建议：

1. 基础字典：渠道、意向等级、基础类型、岗位、组织架构。
2. 画具管理：画具列表、购买、销售记录。
3. 订单管理：订单列表、订单详情、作废、支付相关。
4. 学员管理：学员列表、详情、账户、考勤。
5. 课程/班级/排课。
6. 退款、财务、数据中心。

建议目录：

```text
api/
├── resources.php
├── students.php
├── orders.php
├── teaching_aids.php
├── courses.php
├── attendance.php
└── finance.php
```

风险：中。  
原则：一次只拆一个模块，拆完立刻验证并提交。

### 阶段 5：前端拆分与缓存优化

当前 `static/js/main.js` 仍然很大。建议在 API 稳定后再拆：

```text
static/js/
├── main.js
├── api.js
├── modules/orders.js
├── modules/students.js
├── modules/teaching-aids.js
├── modules/courses.js
└── modules/common-cache.js
```

优先优化：

- 字典数据缓存统一管理。
- 页面首次加载和切页加载分离。
- 弹窗打开时避免重复拉相同校区/学科/员工数据。
- 对列表页加入加载状态和请求取消，避免快速切页时旧请求覆盖新页面。

风险：中。  
收益：减少重复请求，前端维护更清楚。

### 阶段 6：慢查询专项

建议加入轻量接口耗时日志：

- action 名称。
- 总耗时。
- SQL 关键路径耗时。
- 返回记录数。

优先关注：

- 订单列表。
- 学员详情。
- 考勤页面。
- 财务/收入统计。
- 画具销售记录。

风险：低。  
收益：能精准知道下一步该优化哪个接口，而不是凭感觉改。

## 后续执行原则

- 不做一次性大重构。
- 每次只改一个边界：迁移、公共函数、单个 API 模块、单个前端模块。
- 每次改动后至少执行：
  - `php -l`。
  - 相关接口本地请求。
  - 工作区 diff 检查。
  - Git 提交。
- 保持 `develop` 可运行，重构工作优先在 `codex/` 分支推进。
