# 性能优化与架构拆分记录

> 更新日期：2026-07-13
> 当前阶段：第四阶段进行中，基础字典、基础设置、画具、优惠配置、订单查询、订单作废和报价写接口七批 API 已拆分。
> 当前基线：`851f99c`；模块化路由 57 个，`index.php` 原 switch 剩余 105 个 action，入口约 9,700 行。
> 暂停影响：可以在当前架构上继续开发新功能；已拆功能进入对应 `api/*.php`，未拆功能仍由 `index.php` 兼容处理。

## 背景

当前项目长期采用单体 `index.php`：数据库连接、建表迁移、兼容字段补丁、API 路由、HTML 页面都集中在一个文件里。早期开发效率高，但随着模块增加，出现以下问题：

- 每个 API 请求都会经过同一个入口，容易把初始化成本叠加到所有页面加载上。
- `index.php` 文件过大，改动冲突和误伤风险上升。
- API、HTML、迁移逻辑混在一起，排查问题时边界不清。
- 后续继续增加活动、订单、画具、财务等模块时，维护成本会越来越高。

## 风险与回退

### 已控制的风险

- 第一阶段没有拆业务 API，没有拆 HTML 页面，也没有改变主要请求参数。
- 数据库迁移逻辑只是从 `index.php` 移动到 `migrations/bootstrap_schema.php`。
- `ensureSchema($db)` 仍在入口执行，但正常请求只读取 `schema_migrations`。
- pending 迁移通过 MySQL advisory lock 串行执行。
- 保留 `?migrate=1` 兼容入口，日常操作使用 CLI。

### 仍需注意

- `migrations/bootstrap_schema.php` 仍是历史兼容基线，后续数据库变更必须新增版本文件，不能继续堆入基线。
- 当前迁移只支持向前执行，没有自动 down migration；生产变更仍需备份和独立回退 SQL。
- 继续拆 API 前，必须保证每一步都有可运行验证和 Git 提交。

### 回退方式

如果第一阶段出现问题，可以回退提交：

```powershell
git revert bfb3d19
```

迁移框架目前不自动回滚数据库。涉及破坏性变更时，必须先备份并随迁移提供人工回退 SQL。代码回退后可执行：

```powershell
php migrations\migrate.php --status
```

录单与支付批次不得直接搬代码，必须先完成以下设计：

1. 为一次录单请求增加可重放的幂等标识，防止前端重复点击生成重复父子订单。
2. 父订单、全部子订单、账户余额、账户流水、资源转化状态和学员类型变更必须处于同一事务边界。
3. 余额支付使用 `SELECT ... FOR UPDATE`；报价方案和优惠信息在事务开始前后都要防止并发变化造成金额漂移。
4. 在隔离测试数据库中覆盖中途失败、死锁重试、重复请求、混合支付和金额不匹配；生产数据只验证无副作用路径。
5. 保存拆分前响应和关键表计数，迁移后逐字比较错误响应并核对数据库副作用。

阶段 4 完成标准：所有业务 action 都有明确模块归属，`index.php` 只保留启动、兼容分发、导入导出入口和 HTML 页面，不再继续增加新的业务 switch case。

当前目录：

```text
api/
├── router.php
├── dictionaries.php
├── organizations.php
├── settings.php
├── teaching_aids.php
├── discounts.php
└── orders.php
```

风险：高；支付、考勤、退款批次为极高风险。
原则：一次只拆一个业务边界，保持 action 和响应兼容，完成后立即验证。

### 阶段 5：前端拆分与缓存优化

当前 `static/js/main.js` 约 13836 行。阶段 5 在对应后端 API 边界稳定后推进，不等待阶段 4 的所有模块一次性完成。

目标结构：

```text
static/js/
├── main.js
├── api.js
├── modules/orders.js
├── modules/students.js
├── modules/teaching-aids.js
├── modules/courses.js
└── modules/common-cache.js
```

优先优化：

- 第一批：抽离 `api.js`，统一 GET/POST、错误处理、请求超时、短期缓存和缓存失效。
- 第二批：抽离 `modules/orders.js`，覆盖报价、订单列表、订单详情、优惠选择和录单入口。
- 第三批：抽离 `modules/students.js`，覆盖学员详情、账户、退费和上课记录。
- 第四批：抽离 `modules/teaching-aids.js`，覆盖画具管理、销售和商品选择。
- 第五批：抽离 `modules/courses.js`，覆盖课程、班级、排课、教室和考勤视图。
- 最后抽离 `common-cache.js`，统一校区、学科、员工、字典和基础设置缓存。

每批必须处理：

- 页面首次加载和切页加载分离。
- 弹窗打开时避免重复拉取相同校区、学科和员工数据。
- 列表请求使用 `AbortController` 或请求序号，防止旧响应覆盖新筛选结果。
- 写操作成功后按数据域失效缓存，禁止依赖固定时间等待刷新。
- 保持现有全局函数兼容；HTML 中的 `onclick` 全部迁移前不能直接删除旧导出名称。

验证：

- `node --check` 覆盖所有拆分后的 JS 文件。
- 桌面和移动端分别验证导航、列表筛选、弹窗、保存、返回和刷新流程。
- 浏览器控制台无未定义函数、重复事件绑定和未处理 Promise rejection。

风险：中。
收益：减少重复请求，前端维护更清楚。

### 阶段 6：慢查询专项

先加入轻量接口耗时日志，不在没有数据的情况下盲目增加索引。

记录字段：

- action 名称。
- 请求 ID。
- 总耗时。
- SQL 关键路径耗时。
- 返回记录数。
- 是否命中缓存。
- 慢请求使用的筛选条件摘要，不记录手机号、姓名等敏感原值。

阈值建议：

- 总耗时超过 `500ms` 记录 warning。
- 单条 SQL 超过 `200ms` 记录 SQL 标签和耗时。
- 导入、导出和迁移接口单独设置阈值，不与普通列表混算。

优先关注：

- 订单列表。
- 学员详情。
- 考勤页面。
- 财务/收入统计。
- 画具销售记录。

执行流程：

1. 收集至少一个真实业务周期的耗时分布。
2. 对 P95/P99 慢接口使用 `EXPLAIN` 检查全表扫描、临时表、文件排序和相关子查询。
3. 新增索引必须通过版本迁移，记录优化前后执行计划和耗时。
4. 优先减少 N+1、重复查询和无条件大结果集，再考虑缓存。
5. 缓存只用于低频变化的字典/设置数据，订单、余额、考勤和退款不使用不带版本的长期缓存。

风险：低。  
收益：能精准知道下一步该优化哪个接口，而不是凭感觉改。

### 阶段 7：自动化回归与发布保障

当前验证以 `php -l`、本地 HTTP 请求和人工响应基线为主。继续拆支付、考勤和退款前，应增加可重复执行的自动化保障。

计划：

- 增加只读 API 冒烟脚本，检查 HTTP 状态、JSON 可解析性、关键字段和分页外形。
- 为模块路由增加测试，验证无重复 action、handler 可调用和路由数量变化。
- 为数据库迁移增加空库执行、已有库升级、重复执行和并发锁测试。
- 使用独立测试数据库覆盖余额支付、订单作废、报价全量替换、考勤扣课、退款和回滚场景。
- 增加提交前检查脚本：PHP lint、JS syntax、迁移状态、API smoke、`git diff --check`。
- 后续接入 CI 时禁止使用开发数据库凭据，测试数据必须可重建和销毁。

完成标准：高风险写接口的成功、拒绝、重复请求和中途失败路径都能自动验证，发布不再依赖单次人工点击。

风险：中。
收益：降低继续拆分和开发新功能时的回归成本。

## 后续执行原则

- 不做一次性大重构。
- 每次只改一个边界：迁移、公共函数、单个 API 模块、单个前端模块。
- 每次改动后至少执行：
  - `php -l`。
  - 相关接口本地请求。
  - 工作区 diff 检查。
  - Git 提交。
- 保持 `develop` 可运行，重构工作优先在 `codex/` 分支推进。
